# Clean Code for AI-Assisted Development

Code generated by a language model is fast to produce and easy to over-produce. These habits
keep generated changes small, honest, and reviewable. They apply to any agent writing code on a
human's behalf.

## Common failure modes

| Failure mode | Related rules | Habit that prevents it |
| --- | --- | --- |
| Re-implementing a helper that already exists | G5 | Search the codebase for an existing function, type, or constant before writing a new one |
| Wide, sweeping diffs for a small request | G12, G32 | Change only what the task needs; list extra cleanups as suggestions |
| Speculative abstractions and options nobody asked for | G12, Simple Design rule 4 | Build for today's requirement; add the abstraction at the third use |
| Comments that narrate the edit ("now we call X") | C1, C3 | Write comments only for *why*; leave history to the commit message |
| Invented APIs, flags, or package names | G2, G21 | Check the real signature in source or docs before calling it |
| Swallowed exceptions and broad catch blocks | G4, G26 | Handle specific errors, add context, or let them propagate |
| Weakening or deleting a failing test to go green | G4, T4 | Fix the cause; if the test is wrong, say why and change it deliberately |
| Muting the linter, type checker, or warnings | G4 | Fix the finding; suppress narrowly with a stated reason only when unavoidable |
| Inconsistent style with the surrounding code | G11, G24 | Read neighboring files first and copy their conventions |
| Copy-pasted blocks with tiny variations | G5 | Extract the shared part, parameterize the difference |
| Hard-coded values, URLs, secrets, and sizes | G25, G35 | Use constants or configuration; never embed secrets |
| Big untested additions | T1, T3 | Add or update tests with the change and run them |
| Dead code left behind by an approach change | F4, G9 | Delete the abandoned path before finishing |

## Working agreement

1. **Read before you write.** Open the file, its callers, and its tests. Match naming, error
   handling, and layout already in use.
2. **Make the smallest correct change.** A reviewer should be able to hold the diff in their head.
3. **Tests travel with code.** Add a test that fails without your change; run the suite and the
   linter before declaring success.
4. **Tell the truth about verification.** Say what you ran and what you did not. Never claim a
   test passed that you did not run.
5. **Leave one trail of cleanup, not ten.** Apply the Boy Scout Rule to the code you touched,
   in one or two safe improvements, and mention them.
6. **Surface decisions.** If you chose between designs, or deviated from a rule, state it in a
   sentence so the human can overrule you.
7. **Do not touch what you were not asked to.** Generated files, lock files, vendored code, and
   unrelated modules stay as they are.

## Prompts that work well

- "Review this diff against the clean-code skill; report Blockers and Majors only."
- "Refactor `OrderService` for G30 and G14 only; do not change behavior; run the tests."
- "Explain smell G36 with an example in our language."
- "Boy Scout pass on the files you just edited; keep it to two small improvements."
